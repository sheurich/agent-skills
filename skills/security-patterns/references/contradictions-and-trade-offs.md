# Contradictions and trade-offs

- Allow-list versus deny-list for shell, inside one organization: `coop/main/.claude/settings.json` makes Bash default-deny with a narrow enumerated allow-list, while `claude-code-config/main/settings.json` and `codex-config/main/hooks/block-dangerous-command.sh` make it default-allow with a short known-bad list. Least privilege favours the allow-list; the deny-list only stops what someone thought to enumerate.
- Blocking `wget ... | bash` but not `curl ... | bash`, while shipping the unblocked form: the deny patterns in `claude-code-config/main/settings.json` and `codex-config/main/hooks/block-dangerous-command.sh` match only `wget`, yet `claude-code-devcontainer/main/Dockerfile`, `coop/main/README.md`, and `datasig/main/.github/workflows/release.yml` all install tooling via `curl ... | bash`/`| sh` — the last inside a job holding `id-token: write` and `contents: write`. Least privilege favours blocking both forms and installing pinned artifacts with checksum verification, including in the operator's own build tooling.
- Default blast radius differs between the two main harness configs. `codex-config/main/config.toml` disables command network access outright and denies in-workspace secret reads. `claude-code-config/main/README.md` documents no network restriction unless `/sandbox` is opted into. It also accepts that its sandbox leaves reads unrestricted, so the agent can still read `~/.ssh`, `~/.aws`, and the like. Least privilege favours the Codex posture: deny network and restrict reads by default, then widen deliberately.
- In-workspace secret-file denial exists in one sibling config and not the other: `codex-config/main/config.toml` denies `**/.env`, `**/.env.*`, `**/*.pem`, `**/*.key` inside the writable workspace; `claude-code-config/main/settings.json` covers only home-directory paths. Least disclosure favours having the in-workspace rule, since an un-gitignored secret in the working tree is the likeliest one present.
- A file-based credential deny-list next to full environment inheritance: `codex-config/main/config.toml` sets `[shell_environment_policy] inherit = "all"`, passing every exported cloud and CI credential into the session while carefully denying reads of `~/.aws/**` and `~/.npmrc`. Least disclosure favours restricting inherited variables to a named set; the two controls are not reconciled anywhere in the docs.
- A security control relaxed for environment convenience: `claude-code-devcontainer/main/post_install.py` sets git's `safe.directory = *`, disabling the CVE-2022-24765 ownership check for every repository the container touches, to work around a bind-mount UID mismatch. Least privilege favours scoping the exception to the mounted workspace path, which was available and not used.
- Bypass mode is universally said to require isolation but is rarely wired to it: `claude-code-config`, `codex-config`, and `coop/main/docs/trust-model.md` all state the requirement, yet only `coop` and `claude-code-devcontainer/main/post_install.py` structurally guarantee it, while a `claude-yolo` alias or a `--yolo` flag applies bypass with no check that any boundary exists; `micro/main/action.yml` substitutes a disposable runner, a `contents: read` token, and a SARIF-only channel, which are real but are outer-environment controls, not the per-action approval they replace. Least privilege favours making the pairing structural and treating outer isolation as a compensating control, not an equivalent one.
- Two sibling installers disagree on fetching configuration at install time. `claude-code-config/main/.claude/commands/trailofbits/config.md` fetches each config file live from `raw.githubusercontent.com` via WebFetch. `codex-config/main/.agents/skills/install-codex-config/SKILL.md` instead forbids fetching configuration over the network, GitHub included. Least privilege favours the local-only installer. A network fetch makes every update a fresh supply-chain trust decision. The fetch tool can also paraphrase away a rule's scoping frontmatter.
- The deterministic skill scanner cannot see some of the attacks its sibling repository demonstrates. `skills-curated/main/scripts/scan_plugin.py` has no detector for bulk environment enumeration. Its text scan skips any file with a null byte in its first 8 KB. So the `os.environ.items()` dump and the DOCX-smuggled payload in `overtly-malicious-skills` pass by pattern alone. The bytecode-poisoned variant is caught only by the separate `.pyc` and `__pycache__` checks. The security checks in `review-plugin.md` list neither bulk environment enumeration nor binary-asset smuggling nor reviewer-directed persuasion. One position holds that the scanner gates imports. The other holds that the human deep review carries the load. Least privilege favours the latter, plus adding the missing detectors.
- Verification scaffolding: `skills/main/AGENTS.md` says that adding prompt text asking the model to re-check its answer measurably worsens output. Yet `fp-check`, `zeroize-audit`, and `vulnerability-triage-brocards` are built entirely on repeated structured re-verification. The repository's own resolution is that the mechanism differs. A hook, script gate, or ledger check does not carry the cost a vague prompt phrase does. Least privilege favours keeping the deterministic gates while stripping the prompt phrasing, not the reverse.
- Cooperative hooks presented alongside real boundaries: `claude-code-config/main/README.md` states plainly that hooks are soft guardrails rather than hard barriers. It adds that an injected prompt may be able to circumvent them. The plugins that rely on returning `permissionDecision`/`ok` JSON (`gh-cli`, `fp-check`) or on `PATH` shims (`modern-python`) never state that limitation. `post-patch-validation` and `devcontainer-setup` do distinguish their guarantees. Least privilege favours labelling each control as advisory or enforced. Rely on the OS-level control for the threats that matter.
- The marketplace does not apply its own supply-chain standard to itself: `skills/main/plugins/zeroize-audit/.mcp.json` fetches and executes `git+https://github.com/oraios/serena` unpinned at every session start, which `supply-chain-risk-auditor`'s own criteria would flag in any target project. Least privilege favours pinning; there is no argued position on the other side, only an omission.
- Credentials forwarded into an otherwise isolated sandbox: `devcontainer-setup` gives generated containers genuine network isolation and a read-only mount of their own config, then forwards `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_API_KEY` via `remoteEnv`, while `post-patch-validation` refuses to forward credential-shaped variable names even on explicit request. Least disclosure favours the refusal posture, or a short-lived container-specific credential, or the capability-token proxy in `coop/main/docs/credential-proxy.md`.
- Clone-to-temp trades one exposure for another: `skills/main/plugins/gh-cli/hooks/intercept-github-fetch.sh` correctly redirects file fetching to `gh repo clone ... --depth 1` into a session-scoped temp path, but that leaves a full attacker-authored tree on local disk at a predictable location until `SessionEnd`, where a build tool, editor, or another agent may auto-execute something inside it. Least privilege favours the authenticated clone plus explicit containment of the clone directory, not one or the other.
- A marketplace with no category boundary between rigorous and recreational skills: `let-fate-decide` advertises itself as a hypothesis-generation aid using `secrets.randbelow()`. It claims suitability for security, audit, and correctness workflows. The validator checks its metadata exactly as it checks the audit skills'. Least privilege favours an operator-side allowlist for engagement-relevant plugins, since the marketplace provides no suitability flag.
- The MCP wrapper exempts primitives from its own headline gate. `mcp-context-protector`'s `list_resources()`/`read_resource()` proxy downstream regardless of approval. A code comment says resources stay available whatever the config approval state, unlike prompts and tools. Only `notifications/tools/list_changed` resets approval. Prompt and resource change notifications explicitly do not. Resource and prompt content is as attacker-controllable as a tool description. So least privilege favours gating every primitive and treating every change notification as approval-resetting.
- ANSI neutralization is unconditional where a human reads and opt-in where the model reads: `approval_cli.py` always makes escape sequences visible, while `MCPWrapperConfig.visualize_ansi_codes` defaults to `False` in the live tool-call path. Least disclosure favours enabling it by default in the path that feeds the model's context, which is the one the README's feature list implies is protected.
- Interface pinning read as behaviour pinning: `MCPServerEntry`'s hashes cover name, description, parameters, and output schema, and tool removal needs no re-approval, so a server can keep a byte-identical declared interface while changing what the tool does. The pinning is worth having; least privilege favours documenting it as interface-only and keeping a separate control (scoped credentials, response guardrails) for backend drift.
- Two repositories encode opposite classifier defaults: `aifirst-insecure-agent-labs/main/config/nemo/config.yml` tells the classifier to answer no, meaning allow, whenever it is uncertain, with no output-side rail at all. `mcp-context-protector` fails closed on both approval and confirmation. Least privilege favours fail-closed; the fail-open instruction converts every classifier miss into an allowed request by design.
- Recommending an LLM guardrail does not close a channel bypass. `pajaMAS/main/defense_mas` shows an LLM content check missing a payload that arrives via URL anchor. `aifirst-insecure-agent-labs` shows a regex filter missing an encoded payload. Both are labelled naive examples, so the recommendation is not disputed. Least privilege favours scanning every channel rather than upgrading the classifier on one channel.
- A shared pagination base without a maximum: `hackerone-mcp` caps `page_size` at 100 in both schema and handler, while `slither-mcp`'s `PaginatedRequest.limit` validates only a lower bound and relies on each tool to add its own cap. Least privilege favours the mandatory cap in the shared base, so a new tool cannot silently ship uncapped.
- Uneven command handling in the tool whose job is to be the security layer: `mcp-context-protector` launches its downstream server via `self.child_command.split()` with no quoting support. It documents the fragility by warning operators to take care when escaping shell metacharacters. `hackerone-mcp` hardcodes its endpoint and constrains every parameter. Not a runtime vulnerability, but least privilege favours argv-list configuration over a single command string wherever the format allows.
- CI hardening baseline is inconsistent across repositories in the same organization: `fickling/master/CLAUDE.md` documents SHA-pinning and `anamorpher/main/.github/workflows/ci.yml` follows it with `persist-credentials: false` throughout, while `datasig`'s workflows reference `actions/checkout@v4` and friends by mutable tag with no credential-persistence setting. An agent told to match org conventions gets two answers; least privilege favours the SHA-pinned, credential-disabled form.
- Documented intended use versus what the code does by default: `anamorpher/main/backend/app.py` ends with `app.run(debug=True, host="0.0.0.0", port=5000)` and applies `CORS(app)` with no origin allowlist, while the README frames the tool as a local demo. Least privilege favours enforcing the context in code — loopback bind, debug gated on an environment check — rather than in prose.
- One severity scale for two kinds of evidence: `fickling`'s ordered severity mixes allowlist and blocklist violations with heuristics. Its own `SECURITY.md` calls one of them, the `UnusedVariables` heuristic, intentionally weak. A single `max_acceptable_severity` threshold governs both. An operator loosening the threshold implicitly trusts heuristics as much as allowlist violations. Least privilege favours separating the two signal classes rather than tuning one threshold across both.
- Scanners disclaim guarantees while automation wants to gate on them. The `--check-safety` help of `fickling` says results may not be correct. `datasig`'s `comparison_accuracy()`, CompChomper's self-declared limitations, and `awesome-ml-security/main/impossibility_research.md` agree. All say a clean result is risk reduction, not proof. That conflicts with any pipeline that auto-approves a model download, dataset ingestion, or dependency update on a clean scan. Least privilege favours keeping human review in that path and treating a clean scan as one input.
- Dual-use PoCs shipped runnable without isolation instructions: the README of `sleepy-pickle-public/main` disclaims being a ready-made offensive tool. Yet the repository ships a working payload. That payload enumerates the process's open files and re-infects sibling pickle artifacts. Least harm favours reproducing these demos only inside a disposable VM or container. The repository neither enforces nor instructs this.
- Module-level versus symbol-level allowlisting, with no stated rule: `fickling` blocks whole modules (`torch.jit`, `numpy.f2py`) in one place and allowlists exact symbols in another, and the petastorm bypass in `sleepy-pickle-public` shows what happens when whole-package allowlisting is used where symbol scoping was required. Least privilege favours writing the rule down explicitly — block a whole module only after verifying no symbol in it is safe; otherwise allowlist by exact symbol — and the same reasoning applies to allowlisting an entire MCP server rather than its specific tools.
